# NX2Linux: assumptions about functions, builds and addresses

Every assumption the recompilation work (ARM64 Switch modules → x86_64 Linux) relies on, with the date it was made and what would confirm or refute it. Newest last.

## 2026-11-01 (T1: the synthetic fixture and `dm/tools/arm64_survey.py`)

| # | Assumption | Why it is made | How to confirm |
|---|---|---|---|
| H1 | Inside a function the unwind data (`.eh_frame_hdr`) describes, every word is an instruction; a word that does not decode is an error, not data. | The fixture has no literal pools. `nso_code.data_blocks` only finds data between functions. | Run `arm64_survey.py` on a retail module you own, outside this repository: count the `SurveyError`s. A compiler can put a literal pool or a jump table inside a function, so expect some. |
| H2 | A stretch of text no FDE covers is a data block, padding or an SDK wrapper `svc #n; ret`; nothing else is treated as code. | `nso_match.py` (`Image._callee`) makes the same assumption for the SDK's system call wrappers. | Compare the survey's gaps with `nso_code.data_blocks` and Ghidra's view (`nso2elf.py`) on a module you own. |
| H3 | A direct branch that leaves its function and does not land on an FDE start is `unknown`, not an error. | A tail call or a jump into a function the unwind data lacks is possible; the survey only reports it. | The survey lists these targets on a module you own: each should be a function start in Ghidra. |
| H4 | The hand-made encoders in `engine/dm/tools/tests/arm64_fixture.py` (`ADDS`, `SUBS`, `MUL`, `MOVZ`, `BL`, `BCOND`, `CBZ`, `SVC`…) encode what their names say. | They are written from the Arm Architecture Reference Manual. | `test_encodings_decode_as_intended` compares each with Capstone 5. A second decoder (Unicorn or qemu-aarch64 as the ARM64 reference, T2) would be an independent check. |
| H5 | The reference ARM64 behaviour will come from Unicorn (instruction and flag tests) and `qemu-aarch64` (whole functions). Not decided yet. | Neither is installed on this machine (2026-11-01); the Mac Apple Silicon option is not available here. | Téo's choice; install one and run the fixture's `arith` function in it. |
| H6 | Capstone 5 is the decoder (`patch_nso.py` refuses Capstone 6). | `patch_nso.py` header. | `pip install "capstone>=5,<6"`; `_md()` in `arm64_survey.py` checks the version. |

Not assumed, only unknown: how the Switch's retail modules lay out their code (the survey has run on the fixture only), and which functions of a real game call `svc` outside the SDK wrappers.

## 2026-11-01 (T3: branches, memory, calls — `aot_lift.py`, `aot_runtime.cpp`)

| # | Assumption | Why it is made | How to confirm |
|---|---|---|---|
| H7 | A `ret` returns to the caller of the lifted function (the C return); x30 is not consulted. | `__remill_function_return` ends the lifted function; direct `bl` is a C call. | Code that rewrites x30 before `ret` (longjmp-like unwinding, coroutine switches, the SDK's context switch) would break this. Search a real module you own for `ret` after an `x30` write that is not a reload from the stack; T4/T5 must handle or refuse it. |
| H8 | A `br` is a tail call to a function entry. A jump into the middle of a function (a jump table) is an explicit error. | The runtime's table holds function entries only. | Count `br` instructions in a real module with `arm64_survey.py` (kind `ibranch`) and check how many land inside the same function. Jump tables need their cases resolved at translation time. |
| H9 | The guest memory is a few flat regions; an unaligned access to normal memory is allowed and not atomic. | AArch64 normal memory allows it. | Not for Device memory or atomics: do not apply to those. |
| H10 | Floating point, SIMD and `svc` are not translated yet; byte, halfword and pair exclusives (`ldxrb`, `stxrh`, `ldxp`, `stxp`) and the LSE atomics (`ldadd`, `swp`, `cas`...) are not decoded. | Remill refuses them (LiftError); the runtime has no FP intrinsics (LinkError). | Re-run the scan of those mnemonics after each Remill update. The Switch's A57 cores have no LSE, but compilers emit `ldxrb`/`stlxrb`/`ldxp` for byte and 128-bit atomics: check a real module for them before T7. |
| H11 | An exclusive store is a compare-and-swap against the value the exclusive load read (QEMU's model), not a hardware monitor: a store of the same value by another thread between the two goes unseen (ABA). | Remill's monitor had no value at all. | Lock-free code that depends on ABA detection (rare: tagged pointers avoid it) would need a version counter; none is known in the SDK. A real module's atomics (count `ldaxr` loops) must run threaded in T5. |
| H12 | On an x86 host, `stlr` costs a full fence (the store->load barrier that keeps it ordered with a later `ldar`). | STLR and LDAR are sequentially consistent with each other on AArch64. | Measure the cost on a real module's lock-heavy code; weaken only after showing no `ldar` follows. |

## 2026-11-01 (T4: the JIT fallback — `aot_jit.cpp`, dynarmic)

| # | Assumption | Why it is made | How to confirm |
|---|---|---|---|
| H13 | dynarmic is taken from `azahar-emu/dynarmic` at commit `a466015` (2026-09-26), built with Boost 1.90 headers and `CMAKE_POSITION_INDEPENDENT_CODE=ON`. | `merryhime/dynarmic`, its original home, no longer answers; `azahar-emu/dynarmic` and the `yuzu-mirror/dynarmic` archive do. The fork is still committed to. | Re-run `git ls-remote` on both before relying on it; pin the commit in whatever build file the project ends up with. License: 0BSD (`LICENSE.txt`). |
| H14 | A JIT run ends when the code reaches the address the AOT caller left in x30. | `ret` is `br x30`; x30 is kept real so that the return addresses JIT code saves on the stack are true ones (a first version used a sentinel, and the stack differed from the reference's). | Code that returns somewhere else than x30 (a context switch, longjmp-like unwinding) would run on in the JIT instead of returning. Same family as H7. |
| H15 | **Réglée en T5 (2026-11-01).** ~~The code cache is per host thread (16 MB each) and a write invalidates only the writing thread's cache.~~ Now a write by any thread, AOT or JIT, reaches every Jit that compiled from that page (see H22). | dynarmic's `Run` is not reentrant; sharing a cache across threads is not wired. | Two threads where one rewrites code the other already compiled would run stale code. T5 (threads) must invalidate every thread's JIT, or share one cache. |
| H16 | JIT code reads its instructions from guest memory: the code region must be mapped. | `MemoryReadCode` reads the regions the runtime holds. | A module whose text is mapped elsewhere than in `aot_map` regions has no code to JIT: the error says `no code to run at <address>`. T6 (loader) maps it. |
| H17 | An entry into an AOT function's address from JIT code leaves the JIT and resumes at x30 on return. | The entry is refused as code (NoExecuteFault), which stops the run. | A jump (not a call) from JIT code into an AOT function returns to whoever x30 names, which is right for a tail call; a jump that expects to *continue* there does not exist for entries. |
| H18 | SIMD and floating point are available in JIT code (dynarmic translates them) while the AOT code cannot lift them yet; the vector registers are copied both ways at each transition. | `State.simd` and dynarmic's `SetVector` hold the same 32 x 128 bits. | Not tested (no fixture function uses a vector register). T7 will meet them. |

## 2026-11-01 (T5: svc, guest CPU state, threads)

| # | Assumption | Why it is made | How to confirm |
|---|---|---|---|
| H19 | The Horizon service handler has the signature of `svc_dispatch(num, regs, orig_addr)` (`hle_svc.c`): `regs` is x0..x30, the handler writes its answers back into `regs` (x0 first), its return value is not used by the recompiled code. | `hle.c` `gate_dispatch` passes `regs` the same way and reads results from it; `regs[0]` is the answer. | Link the real `hle_svc.c` once T6 removes its Mach-O parts (`vm_read_overwrite`, `mach_task_self`): it calls `svc_thread`, `mem_init` and uses real `mmap`, so its memory is host memory at real addresses, not the bounded regions of `aot_runtime.cpp`. **Not done in T5**: the tests use a stand-in handler. |
| H20 | An `svc` is the AArch64 `svc #n` with n < 0x10000; Horizon numbers are small. The number reaches the handler as `State.hyper_call_vector`. | Remill sets it in `CallSupervisor`. | Confirmed by the tests for 0x2A, 1 and 99 against Unicorn. |
| H21 | Guest memory a service creates (MapMemory, SetHeapSize) is a new bounded region (`aot_try_map`), visible to running guest threads at once; a removed region keeps its host memory until `aot_unmap_all`. | Readers walk a fixed array without a lock; freeing at once would let a thread read freed memory. | A game that maps and unmaps in a loop (heap resizing) grows the host memory: count `regions`, and recycle by size once real modules run. The table holds 512 regions. |
| H22 | A tight guest loop in JIT code is interrupted every 2**18 cycles (`kSlice`) to see what other threads asked for. | dynarmic checks the halt flag between linked blocks only when its cycle counter runs out (`a64_emit_x64.cpp`, `LinkBlock`): `b .` ignored a halt. | The test `test_a_thread_spinning_in_jit_code_is_stopped_by_a_rewrite`. The cost of the slicing was not measured. |
| H23 | `ic ivau` / `ic ialluis` invalidate all threads' compiled code (they broadcast on the hardware). | `InstructionCacheOperationRaised` calls the same global invalidation as a store. | Not exercised: no test fixture runs `ic`. A game that generates code will. |
| H24 | The thread pointers are plain per-run inputs: `tpidr_el0` (read and written by the guest, returned) and `tpidrro_el0` (read only). x18 is an ordinary register. | Remill's `State.sr` holds both; Horizon puts the thread-local region in `tpidrro_el0`. | The real loader (T6) must set them per guest thread as `thread.c` does (TLR at +0x1f8 is the current thread, ID at +0x110). **Not wired to `thread.c`**: it is Mach-O/Apple specific today. |

## 2026-11-01 (T6: ELF modules and manifest — `elf_module.py`)

| # | Assumption | Why it is made | How to confirm |
|---|---|---|---|
| H25 | The dynamic symbol count is (DT_STRTAB - DT_SYMTAB) / 24: the string table starts where the symbol table ends. | `host/loader.c` `parse_dynamic` computes `nsym` the same way for every module it loads. | A module where something sits between the two raises ModuleError. Run `elf_module.py` on every retail NSO available and count the errors. **Not done: no game module here.** |
| H26 | A function entry the unwind data does not describe is found as the target of a direct `bl`/`b` outside every known function, as an exported function symbol, or as a function pointer a RELATIVE relocation stores. A stretch found that way is scanned up to its first `b`/`br`/`ret`. | PLT stubs and the SDK's `svc` wrappers have no FDE (T1 survey: "svc stubs", "gaps"). Without their entries a `bl` to them cannot link. | Compare the entries with a disassembler's on a real module: a stub reached only through a pointer built by `adrp`+`add` (not RELATIVE) is missed, and calling it goes through the JIT instead. |
| H27 | Module memory is one region per module with no page permissions: a guest write to code is not a fault. | `aot_runtime.cpp` regions have no protection bits. The JIT invalidation (T5) means such a write is at least *seen*. | A module that writes to its own text expecting a crash (a guard) behaves differently. The Mach-O loader seals text read-only (`mprotect`). |
| H28 | Module bases are assigned from 0x08000000 in load order with 64 KiB between modules, not where Horizon puts them (randomised by the ASLR of ldr). | The recompiled code is position independent (adrp/add) and lifted at its final address. | Nothing in the engine depends on the base; a game that stores absolute addresses it computed itself is fine as long as it reads them back from the same run. |
| H29 | An *import* is an address with no code behind it (from 0x70000000, 16 bytes apart); calling it runs a host function on the registers (x0..x30 in, x0.. out), like `svc` (H19). The real HLE functions of `hle.c` have the C ABI of the host; they will need a thin adaptor (`regs` -> arguments) per function, or one generic one by signature. | Same convention as the service handler. | **Not wired to `hle.c`/`swhle`**: the tests use Python functions. The size of that adaptor work depends on how many HLE functions take structs by value or floats in v0..v7 (not in `regs`). |
| H30 | A symbol no module and no host function defines is bound to an import that stops with its name when called (an undefined weak one to 0). | `host/loader.c` `resolve_import` binds unknown symbols to logging stubs; failing at the call, not at load, keeps a game that never calls it running. | A game that calls an unimplemented import stops with `unresolved import <name>` and the address. |

## 2026-11-01 (T7: first real module — Balatro, SDK nnSdk, NSO of a retail NSP)

| # | Assumption | Why it is made | How to confirm |
|---|---|---|---|
| H31 | A call (`bl`/`b`) from one function into the middle of another function's unwind range lands on an entry, and that range is split there. | The PLT of every real module has one FDE for the whole table, and each stub is called on its own: without the split, building a module failed with `sub_<plt stub>` undefined (subsdk1). | After the split, the number of `call` entries equals the number of JUMP_SLOT relocations in subsdk1 (193 and 193). main and sdk differ slightly (400 / 388, 8903 / 8934): some stubs are not called directly, some calls are not to stubs. Not investigated. |
| H32 | A leaf function tested with random arguments is a fair sample of the module's code. | Leaves are the only functions testable alone (no callee to supply). | They are 13% of subsdk0 (7,557 of 58,181), small and arithmetic-heavy: calls, indirect branches and svc are exactly what they leave out. The whole-module builds (below) test those only for *building*, not for results. |
| H33 | A case where Unicorn and the AOT code both fault proves nothing. | Both agreeing on a fault shows that the inputs were bad, not that the translation is right. | 53% of the random cases fault on both sides (random pointers into unmapped memory). The 2,658 equal cases are the evidence; 78 of 400 functions never produced one (`inconclusive`). |
| H34 | `Aot.run` does not set the vector registers, so a function that uses them is compared with them at zero on both sides. | `Guest` holds x0..x30, sp, nzcv and the thread pointers. | A function whose result depends on v0..v7 is compared on one input only. FP/SIMD results are the least tested part of everything here. |
| H35 | `remill-lift` takes the function as one hex argument: a function over 60,000 bytes is a LiftError and runs in the JIT. | Linux caps one argument at 128 KiB (`E2BIG` stopped the build of `main`). | The count of such functions in a module (`unliftable` reasons that say "more than the 60000"). A file or a stdin input for the lifter would remove the limit. |

## 2026-11-02 (blocage 2 : tables de sauts)

| # | Assumption | Why it is made | How to confirm |
|---|---|---|---|
| H36 | A `br` is a jump table when, in the up to 400 instructions before it in the same function, the register is a known address plus a shifted/extended entry loaded by `ldrb/ldrh/ldr w/ldrs*` from a known address. | The shapes of LLVM and GCC output, and of Balatro's modules (742 / 3,138 / 642 tables). | The `br`s that look like tables but are not recognised (211 in subsdk0 after widening the window, mostly `ldrb w9,[sp]`-like noise): list them and read a few. A game built by another compiler may use another shape. |
| H37 | The entries of a table are within the function that holds the `br`. | Case blocks follow the dispatch in the same function; a target outside is dropped. | A switch whose cases are outlined into other functions loses those cases to the JIT. |
| H38 | The number of entries is the guard's `cmp reg, #k` + 2, else the targets inside the function. | The guard is the only bound the code gives. | A table longer than its guard (the compiler removed the bound) loses its tail cases to the JIT; the other direction only lifts blocks nobody enters. |
| H39 | A case lifted from its own address with the whole function bytes around it is equivalent to jumping there inside the function. | State lives in the register file and memory, not in the C stack: the original function's `br` is a tail call to the case, which returns for it. | 78 real functions with switches equal to Unicorn (1,152 cases, 2,243 table jumps, 0 fallbacks). A case that returns into the *middle* of its own caller-frame is the shape to look for (not met). |

## 2026-11-02 (blocages 3 et 4 : flottants scalaires, exclusifs octet/demi-mot)

| # | Assumption | Why it is made | How to confirm |
|---|---|---|---|
| H40 | NaN inputs are not handled as ARM does, except that an invalid operation with no NaN input returns the positive default NaN. | x86 and ARM differ in the NaN returned when two operands are NaN (which one, and signalling before quiet), and in the sign of the default NaN. | The tests leave NaNs out of their inputs (`has_nan`) and say so. A game that computes with NaNs and compares the bit patterns would differ; one that tests them with `fcmp` does not. |
| H41 | The cumulative exception flags in FPSR come from the host FPU around each operation. | Remill's semantics clear and read the host flags. | They equal Unicorn's except the inexact flag of integer-to-float conversions and fmadd's underflow (frozen in `test_the_exception_flags_of_the_scalar_batch_agree_except_the_known_ones`). Input-denormal (IDC) is never reported: x86 has no flag for it. |
| H42 | The rounding mode is round-to-nearest-even (FPCR.RMode = 0); FRINTX/FRINTI and the conversions that take the "current" mode use it. | The host FPU is in nearest mode and the semantics do not read FPCR. | A game that sets FPCR.RMode through `msr fpcr` gets the wrong rounding for the instructions that follow the mode. FZ and DN (flush to zero, default NaN) are not modelled either. Grep a module for `msr fpcr`. |
| H43 | A pair store of two Q registers is two independent 128-bit stores, not one 256-bit store. | The memory operand cannot be 256 bits. | A concurrent reader of the pair could see one half written and not the other: neither is guaranteed atomic on the hardware either (a pair store is not single-copy atomic as a whole). |
| H44 | A prefetch (PRFM/PRFUM) and DSB/DMB/ISB have no effect beyond the barrier. | Hints and barriers; DSB is at least a full fence here. | Nothing observable; a spin wait that relies on DSB to drain a write buffer sees it drained (x86 TSO is stronger). |

## 2026-11-02 (NEON)

| # | Assumption | Why it is made | How to confirm |
|---|---|---|---|
| H45 | A 64-bit NEON arrangement (8B, 4H, 2S) is handled on 128-bit registers whose upper half the instruction zeroes, as the hardware does. | The semantics read and write whole 128-bit registers and compute only the lanes the arrangement names. | Every integer and floating-point form compares equal to Unicorn including the upper half (the harness compares all 32 vector registers). |
| H46 | A saturating instruction sets FPSR.QC by `state.fpsr.flat |= 1 << 27`, and QC reaches the guest through `aot_fpsr_get`. | `State.fpsr` holds the bits the cumulative-flag fields of `State.sr` do not. | Equal to Unicorn on all the saturating forms tested. A guest that reads FPSR through the JIT/AOT boundary gets the same. |
| H47 | NEON floating-point lanes use the host's flags for the whole instruction (cleared once, read once), and never report the input-denormal flag. | One flag read per instruction is how the scalar forms work too. | Four forms differ in FPSR out of 678 (frozen in the test). |
| H48 | Crypto instructions (AES, SHA, PMULL, CRC32), exclusive pairs, `cas`/`swp` and `mrs ctr_el0` are not translated and run in the JIT. | They are 0.02% of Balatro's instructions, 14 functions each at most. | Balatro's own use is in its bundled TLS/crypto code: a game that encrypts its saves or streams audio decoders through them would spend its time in the JIT. Translate them when a profile says so. |
| H49 | `LDn`/`STn` of several registers move one element at a time through the memory intrinsics, in the interleaved order of the architecture. | Same order as the pseudocode of the manual (repetition, element, structure member). | 534 forms equal to Unicorn, with and without post-increment. Not atomic as a whole: the hardware does not guarantee it either. |
