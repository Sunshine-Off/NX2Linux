# NX2Linux: assumptions about functions, builds and addresses

Every assumption the recompilation work (ARM64 Switch modules → x86_64 Linux) relies on, with the date it was made and what would confirm or refute it. Newest last.

## 2026-11-01 (T1: the synthetic fixture and `dm/tools/arm64_survey.py`)

| # | Assumption | Why it is made | How to confirm |
|---|---|---|---|
| H1 | Inside a function the unwind data (`.eh_frame_hdr`) describes, every word is an instruction; a word that does not decode is an error, not data. | The fixture has no literal pools. `nso_code.data_blocks` only finds data between functions. | Run `arm64_survey.py` on a retail module you own, outside this repository: count the `SurveyError`s. A compiler can put a literal pool or a jump table inside a function, so expect some. |
| H2 | A stretch of text no FDE covers is a data block, padding or an SDK wrapper `svc #n; ret`; nothing else is treated as code. | `nso_match.py` (`Image._callee`) makes the same assumption for the SDK's system call wrappers. | Compare the survey's gaps with `nso_code.data_blocks` and Ghidra's view (`nso2elf.py`) on a module you own. |
| H3 | A direct branch that leaves its function and does not land on an FDE start is `unknown`, not an error. | A tail call or a jump into a function the unwind data lacks is possible; the survey only reports it. | The survey lists these targets on a module you own: each should be a function start in Ghidra. |
| H4 | The hand-made encoders in `engine/dm/tools/tests/arm64_fixture.py` (`ADDS`, `SUBS`, `MUL`, `MOVZ`, `BL`, `BCOND`, `CBZ`, `SVC`…) encode what their names say. | They are written from the Arm Architecture Reference Manual. | `test_encodings_decode_as_intended` compares each with Capstone 5. A second decoder (Unicorn or qemu-aarch64 as the ARM64 reference, T2) would be an independent check. |
| H5 | The reference ARM64 behaviour will come from Unicorn (instruction and flag tests) and `qemu-aarch64` (whole functions). Not decided yet. | Neither is installed on this machine (2026-11-01); the Mac Apple Silicon option is not available here. | Téo's choice; install one and run the fixture's `arith` function in it. |
| H6 | Capstone 5 is the decoder (`patch_nso.py` refuses Capstone 6). | `patch_nso.py` header. | `pip install "capstone>=5,<6"`; `_md()` in `arm64_survey.py` checks the version. |

Not assumed, only unknown: how the Switch's retail modules lay out their code (the survey has run on the fixture only), and which functions of a real game call `svc` outside the SDK wrappers.

## 2026-11-01 (T3: branches, memory, calls — `aot_lift.py`, `aot_runtime.cpp`)

| # | Assumption | Why it is made | How to confirm |
|---|---|---|---|
| H7 | A `ret` returns to the caller of the lifted function (the C return); x30 is not consulted. | `__remill_function_return` ends the lifted function; direct `bl` is a C call. | Code that rewrites x30 before `ret` (longjmp-like unwinding, coroutine switches, the SDK's context switch) would break this. Search a real module you own for `ret` after an `x30` write that is not a reload from the stack; T4/T5 must handle or refuse it. |
| H8 | A `br` is a tail call to a function entry. A jump into the middle of a function (a jump table) is an explicit error. | The runtime's table holds function entries only. | Count `br` instructions in a real module with `arm64_survey.py` (kind `ibranch`) and check how many land inside the same function. Jump tables need their cases resolved at translation time. |
| H9 | The guest memory is a few flat regions; an unaligned access to normal memory is allowed and not atomic. | AArch64 normal memory allows it. | Not for Device memory or atomics: do not apply to those. |
| H10 | Floating point, SIMD and `svc` are not translated yet; byte, halfword and pair exclusives (`ldxrb`, `stxrh`, `ldxp`, `stxp`) and the LSE atomics (`ldadd`, `swp`, `cas`...) are not decoded. | Remill refuses them (LiftError); the runtime has no FP intrinsics (LinkError). | Re-run the scan of those mnemonics after each Remill update. The Switch's A57 cores have no LSE, but compilers emit `ldxrb`/`stlxrb`/`ldxp` for byte and 128-bit atomics: check a real module for them before T7. |
| H11 | An exclusive store is a compare-and-swap against the value the exclusive load read (QEMU's model), not a hardware monitor: a store of the same value by another thread between the two goes unseen (ABA). | Remill's monitor had no value at all. | Lock-free code that depends on ABA detection (rare: tagged pointers avoid it) would need a version counter; none is known in the SDK. A real module's atomics (count `ldaxr` loops) must run threaded in T5. |
| H12 | On an x86 host, `stlr` costs a full fence (the store->load barrier that keeps it ordered with a later `ldar`). | STLR and LDAR are sequentially consistent with each other on AArch64. | Measure the cost on a real module's lock-heavy code; weaken only after showing no `ldar` follows. |

## 2026-11-01 (T4: the JIT fallback — `aot_jit.cpp`, dynarmic)

| # | Assumption | Why it is made | How to confirm |
|---|---|---|---|
| H13 | dynarmic is taken from `azahar-emu/dynarmic` at commit `a466015` (2026-09-26), built with Boost 1.90 headers and `CMAKE_POSITION_INDEPENDENT_CODE=ON`. | `merryhime/dynarmic`, its original home, no longer answers; `azahar-emu/dynarmic` and the `yuzu-mirror/dynarmic` archive do. The fork is still committed to. | Re-run `git ls-remote` on both before relying on it; pin the commit in whatever build file the project ends up with. License: 0BSD (`LICENSE.txt`). |
| H14 | A JIT run ends when the code reaches the address the AOT caller left in x30. | `ret` is `br x30`; x30 is kept real so that the return addresses JIT code saves on the stack are true ones (a first version used a sentinel, and the stack differed from the reference's). | Code that returns somewhere else than x30 (a context switch, longjmp-like unwinding) would run on in the JIT instead of returning. Same family as H7. |
| H15 | **Réglée en T5 (2026-11-01).** ~~The code cache is per host thread (16 MB each) and a write invalidates only the writing thread's cache.~~ Now a write by any thread, AOT or JIT, reaches every Jit that compiled from that page (see H22). | dynarmic's `Run` is not reentrant; sharing a cache across threads is not wired. | Two threads where one rewrites code the other already compiled would run stale code. T5 (threads) must invalidate every thread's JIT, or share one cache. |
| H16 | JIT code reads its instructions from guest memory: the code region must be mapped. | `MemoryReadCode` reads the regions the runtime holds. | A module whose text is mapped elsewhere than in `aot_map` regions has no code to JIT: the error says `no code to run at <address>`. T6 (loader) maps it. |
| H17 | An entry into an AOT function's address from JIT code leaves the JIT and resumes at x30 on return. | The entry is refused as code (NoExecuteFault), which stops the run. | A jump (not a call) from JIT code into an AOT function returns to whoever x30 names, which is right for a tail call; a jump that expects to *continue* there does not exist for entries. |
| H18 | SIMD and floating point are available in JIT code (dynarmic translates them) while the AOT code cannot lift them yet; the vector registers are copied both ways at each transition. | `State.simd` and dynarmic's `SetVector` hold the same 32 x 128 bits. | Not tested (no fixture function uses a vector register). T7 will meet them. |

## 2026-11-01 (T5: svc, guest CPU state, threads)

| # | Assumption | Why it is made | How to confirm |
|---|---|---|---|
| H19 | The Horizon service handler has the signature of `svc_dispatch(num, regs, orig_addr)` (`hle_svc.c`): `regs` is x0..x30, the handler writes its answers back into `regs` (x0 first), its return value is not used by the recompiled code. | `hle.c` `gate_dispatch` passes `regs` the same way and reads results from it; `regs[0]` is the answer. | Link the real `hle_svc.c` once T6 removes its Mach-O parts (`vm_read_overwrite`, `mach_task_self`): it calls `svc_thread`, `mem_init` and uses real `mmap`, so its memory is host memory at real addresses, not the bounded regions of `aot_runtime.cpp`. **Not done in T5**: the tests use a stand-in handler. |
| H20 | An `svc` is the AArch64 `svc #n` with n < 0x10000; Horizon numbers are small. The number reaches the handler as `State.hyper_call_vector`. | Remill sets it in `CallSupervisor`. | Confirmed by the tests for 0x2A, 1 and 99 against Unicorn. |
| H21 | Guest memory a service creates (MapMemory, SetHeapSize) is a new bounded region (`aot_try_map`), visible to running guest threads at once; a removed region keeps its host memory until `aot_unmap_all`. | Readers walk a fixed array without a lock; freeing at once would let a thread read freed memory. | A game that maps and unmaps in a loop (heap resizing) grows the host memory: count `regions`, and recycle by size once real modules run. The table holds 512 regions. |
| H22 | A tight guest loop in JIT code is interrupted every 2**18 cycles (`kSlice`) to see what other threads asked for. | dynarmic checks the halt flag between linked blocks only when its cycle counter runs out (`a64_emit_x64.cpp`, `LinkBlock`): `b .` ignored a halt. | The test `test_a_thread_spinning_in_jit_code_is_stopped_by_a_rewrite`. The cost of the slicing was not measured. |
| H23 | `ic ivau` / `ic ialluis` invalidate all threads' compiled code (they broadcast on the hardware). | `InstructionCacheOperationRaised` calls the same global invalidation as a store. | Not exercised: no test fixture runs `ic`. A game that generates code will. |
| H24 | The thread pointers are plain per-run inputs: `tpidr_el0` (read and written by the guest, returned) and `tpidrro_el0` (read only). x18 is an ordinary register. | Remill's `State.sr` holds both; Horizon puts the thread-local region in `tpidrro_el0`. | The real loader (T6) must set them per guest thread as `thread.c` does (TLR at +0x1f8 is the current thread, ID at +0x110). **Not wired to `thread.c`**: it is Mach-O/Apple specific today. |
